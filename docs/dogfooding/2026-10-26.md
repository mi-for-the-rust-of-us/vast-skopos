# Dogfooding `vas`, 2026-10-26 — the Me41 rental (two RTX 5090s, one seed each; askesis)

askesis's Me41 (L12): two AR training runs, one per box, ~3.2 h each. Éric rented two RTX 5090s:
- box 1: instance 57787711, South Korea, host 406325, machine 142523, $0.517/h. It is the host of the two 10-25 boxes.
- box 2: instance 57787806, Spain, host 205509, machine 151381, $0.521/h.

Installed `vas` is 0.2.0, read-only, from the launching PC. The offer searches below ran a copy of the
`notes-2026-10-23` branch's release build, for `--host` and `--wide`. Times are CET, read from the commands' output.

## What worked

- **`vas --ssh` showed both boxes and their costs before Éric announced the second one.** At 09:35:43, box 2 already
  stood under box 1 as `loading -> running`, with its `$/H`, age and `COST~`. The money line read `credit $29.31 |

## Notes

1. **A board limited to 450 W in its firmware reads as uncapped.** Box 2's `POWER` read `450W`, with no
   denominator. Box 1, the same model, read `500/600W` and looks capped. One `ssh` to box 2 (09:39:28) gave:

   ```
   power.limit 450.00 W, power.default_limit 450.00 W, power.max_limit 450.00 W, power.min_limit 400.00 W
   enforced.power.limit 450.00 W, clocks.max.sm 3090 MHz, power.draw 33.91 W, P8
   ```

   `power_cell` prints `limit/default` only when the default exceeds the limit. Here limit, default and maximum
   are all 450 W, so nothing on the box can reveal that the board sits below the RTX 5090's reference 575 W.
   The board itself is the cap, and the host cannot lift it (`max_limit` 450).

   - **The cost is known in kind, not yet in size.** A 500 W limit cost 12-15 % per step on 10-23 (that report's
     measurement, confounded with the CPU) and ~8 % on 10-25 (50.7 ms against Texas's 46.9). Today's speed checks give a third and a fourth point on the same job: box 1 at 500 W, box 2 at
     450 W. They will be added below.
   - **Under load, `vas` does show it.** During the training (the `--until` wait, 10:13-10:26), box 2 read
     `450W+power_cap` with `CLOCK` 2182-2212/3090, and box 1 read `500/600W+power_cap` with 2415-2430/3105. The
     clock ratio is ~0.91 and the step-time ratio 0.94. So the gap is the look **before** the deploy, at idle: that is
     when a box is kept or destroyed, and then `450W` reads as uncapped.
   - **What `vas` could add:** a reference board power per GPU model (RTX 5090: 575 W, NVIDIA's figure), and a
     mark when the card's maximum (`power.max_limit`) is below it, e.g. `450W<575`. The default cannot be the
     reference: box 1's default is 600 W, an add-in board above the reference.
     `power.max_limit` is not in the probe's query yet (`index,power.draw,power.limit,power.default_limit,...`).
   - **The offer listing could not be checked for this machine.** `vas offers --no-config --host 205509 --wide`
     (09:42) found no offer left on that host, so whether its `LIMIT W` (`gpu_max_power`) would have read 450 before
     renting stays open. The same search on host 406325 found machine 148821, `verified`, $0.496/h, DLPerf 194.2,
     `LIMIT W` **500**: again the host's cap, in the listing (note 8's new lead in the 10-23 report).
2. **`GPU% (ssh)` read 100 % on an idle card.** Box 1, `running` at 2-6 min of age, read `100%` with `0.0/32G`, `-`
   in `OTHER` and `CLOCK` 2932/3105 in two looks (09:35:43, 09:36:05) and in a third at 09:39:16. One `ssh`
   (09:36:16) read `100 %, 2 MiB, 122.79 W, 37 °C, P0` and no compute process. The utilisation counter is stuck
   while nothing runs: 2 MiB, 37 °C and 123 W are an idle P0 card. Box 2 read `0%`, 34 W, P8.
   - The risk: `100%` beside a box nobody has used yet reads as "someone else is on it", which is the 10-18 worry.
     `OTHER` (`-`) and `VRAM` (0.0) already answer it, but not in the cell that alarms.
   - **What `vas` could add:** a utilisation with no memory held, and no process, could print `100%?`, or a note
     under the table such as `57787711: 100% with no memory held and no process (an idle counter?)`. The probe would
     need `nvidia-smi --query-compute-apps` or the memory figure it already reads.
   - To confirm: how the counter reads once the training holds the card (the speed check, then the run).

Read: a board limited to 450 W costs **+6.5 %** per step against the 500 W cap and **+15 %** against 575 W. On a
~3 h run that is ~11 min and ~$0.10: not worth refusing a box for, but worth showing. Box 1's speed check matched
10-25's 500 W boxes to the tenth of a ms, so its `100%` at idle (note 2) was not another tenant.

For note 8 (DLPerf and caps): `vas --wide` (branch build, 10:15) reads DLPerf **199.2** on box 1 (500/600 W) and
**191.0** on box 2 (450 W board, EPYC 9124). The ratio is 0.96, against a step-time ratio of 0.94. So DLPerf saw this
limit, roughly, where it did not see the 500 W cap of the 10-25 pair (199.2 there too). A limit in the board's own
firmware may be what DLPerf measures, and a cap set by the host may not be.
