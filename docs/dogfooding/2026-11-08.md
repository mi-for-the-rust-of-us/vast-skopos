# Dogfooding `vas`, 2026-11-08: the learning curve, measured with two fresh agents and a mock

Not a rental. The 0.5.0 plan ([`docs/roadmap-v0.5.0.md`](../roadmap-v0.5.0.md), part 4) asks whether a newcomer
can do real tasks from `vas`'s help alone, or from its skill alone, with no guessing of flags. Claude started
two fresh agents (subagents with no knowledge of the repository), each told not to read any file or search
the web:

- **Run 1, the help only:** it could run `vas -h`, `vas --help`, `vas offers -h` and `vas offers --help`,
  but not `vas --skill`.
- **Run 2, the skill only:** it ran `vas --skill` first, and could not run any help.

Both ran `vas` (the `next-0.5.0` branch at `96e0148`, a debug build) against the harness of
[`tests/measure.rs`](../../tests/measure.rs), under WSL. It is a mock of vast.ai, a fake `ssh` and a fake
`nvidia-smi`; nothing reached vast.ai or a real box. The harness was restarted between the two runs. It
holds four boxes, each one task's answer:

- **56533728,** at work under a 400 W limit (`400/575W+power_cap`, `CLOCK 1717/3090`). Its log already holds
  `initial loss`.
- **56558627,** at work on a 450 W board (`450W<575`). Its `initial loss` is written 40 s after the first
  wait asks for it.
- **57787711,** an idle card whose counter reads 100 % (`100%?`).
- **57340012,** `loading`, with vast.ai's message `46b4edaa8d47: Pull complete`.

The offers include the cheaper verified twins of 56533728, plus traps: an unverified offer, a deverified
one, another GPU, and 56533728's own machine.

## The tasks, as a person asks them

1. "Is any of my boxes idle?"
2. "Is any of my GPUs capped, or running below what it should?"
3. "Box 56558627 is starting a training run that writes to /root/runs/<run>/train.log. Wait until it prints
   its first loss (the line contains `initial loss`), but give up after ten minutes. Tell me the line."
4. "Box 56533728 costs too much. Find me a cheaper verified machine like it."
5. "Why is box 57340012 not running?"

## The result: the bar is met by both

Each task was done right by both runs, with no flag guessed. Run 1 ran 8 commands, three of them to read
the help; run 2 ran 7, one of them `vas --skill`. The two runs took about 100 and 115 seconds.

- **Idle:** both named 57787711 from `100%?` and the line under the table.
- **Capped:** both named 56533728 (`400/575W+power_cap`, a limit below the default, the clock held down) and
  56558627 (`450W<575`, the board itself).
- **The wait:** both used `--instance 56558627` with `timeout 600`. A wait that does not name the box ends
  at once on 56533728's line, and both avoided it. Both got exit 0 and `step 0 initial loss 2.3105`.
- **The offer:** both ran `vas --wide --instance 56533728`, then
  `vas offers --gpu RTX_5090 --num-gpus 1 --verified --max-price 0.49 --exclude-machine 100682 --wide`, and
  named 52010001 (the same CPU, host and DLPerf) and 52010003. Neither fell for the unverified offer, which
  was cheaper. Run 2 noticed something the harness did not plant: 52010001 shares its host with the capped
  box, so its cap may follow it. It advised a `vas --ssh` soon after renting.
- **Not running:** both read `loading -> running`, the 3-minute age and the status line as progress, not a
  stuck box.

## Where they stumbled, and what changed

Each stumble below was fixed before the branch went on. Neither fresh agent has been run again on the
fixed text.

- **The marks were taught only in passing (run 1).** The help explained `100%?` and the `POWER` forms in a
  single example, and never `CLOCK` or the `loading -> running` arrow. `vas --help` now has a **Reading the
  table** block: `STATUS`, `COST~`, `GPU% (ssh)`, `OTHER`, `POWER` (with the other reason words), `CLOCK`,
  the last cell and the money line. A test renders a table and checks that each mark it teaches is one the
  table prints.
- **The bare `575W`, and a low clock without a cap (run 2).** The skill now says what they mean: a card at its
  default, at rest. It also explains `CLOCK`.
- **`--log-wait` looked like an overall time limit (run 1).** The help now says, at `--until`, at `--log-wait`
  and in the example, that the wait has no time limit of its own, and that `timeout` gives one and exits 124.
- **`(no line matches)` during a wait (run 2).** Under `--until` the log cell shows the last line matching the
  pattern, so the cell reads `(no line matches)` until the line comes. Neither text said so. Both say it now.
  The skill also lists each state of the log cell and says that `s0` in `s0/train.log` is the run (run 1 had
  taken it for a cut-off path).
- **The match line can land in the middle of the table (both).** It goes to stderr and the table to stdout,
  so on a terminal the two mix. The help says which output goes where. The skill tells an agent to read the
  exit code rather than look for the line.
- **No question row for "is a box idle?" (run 2).** Run 2's first command, plain `vas`, could not tell. The
  skill's table now has the row.
- **`vas offers`, under-taught in the skill (run 2).** It now gives the unit of `--max-price` ($/h, storage
  included), the columns and the `N dropped here` footer. Its recipe is the command both runs built, and it
  says that a host which capped one card may cap the others and that no flag filters on the power limit.
  `vas offers --help` gains the same example and a **Reading the footer** block (run 1 asked about the
  footer too).

## Still open

- **Does a box's `$/H` include its storage, as the offers' does?** Run 1 asked this before it compared the
  two. `vas` shows the API's `dph_total` for both. Whether the instance's figure includes the disk was not
  checked against an invoice, so neither text claims it. It is worth a look at the next rental.
- **Both agents were Claude models, without the repository but not without a general knowledge of command
  lines.** A person new to `ssh` and `nvidia-smi` may stumble where they did not.
