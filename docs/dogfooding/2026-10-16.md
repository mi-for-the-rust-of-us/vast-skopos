# Dogfooding `vas`, 2026-10-16 — the Me35 rental (three RTX 5090s, askesis)

The first real use: three boxes rented for askesis's Me35 (California, Poland, Belgium), a read-only key
(`vastai-skopos`: User Read + Instances Read, no Write, no 2FA).

## Found in the first minute

1. **The account endpoint redirects.** `GET /api/v0/users/current` answers **301**; `vas` follows no redirect
   (a design rule: the key is never re-sent), so the money line read `credit ?`. The official CLI's HTTP library
   follows redirects silently. Fix: request the canonical `/api/v0/users/current/`. Credit then read $30.38.
2. **The API's `ssh_port` is not always the port to connect to.** One box read `ssh_port` 37240 while the
   dashboard's own command used 37241. The official CLI's `_ssh_url` adds 1 on the proxy for Jupyter-launched
   instances (`image_runtype` contains `jupyter`), and prefers a directly mapped `22/tcp` when present. Fix: the
   proxy rule, with the field read and a doctest.
3. **Key file saved by Notepad as `vast_api_key.txt`.** The README warns about it; `vas` could say so too:
   when the file is absent but `<name>.txt` exists, name it in the error. **Done 2026-10-16** (`key::txt_hint`).

## What helped

- The whole fleet in one table with per-box cost so far and the burn rate, before any ssh.
- `credit $30.38 | burn $1.940/h over 3 running | ~15.7 h left at this rate`: the runway number is the one to watch
  on a budget.

## Found while launching

4. **Advertised bandwidth is not the bandwidth you get.** A verified Polish box listed with good up/down on the
   search page measured **1.52 MB/s** of upload to Hugging Face (askesis's preflight floor is 5 MB/s); two other
   boxes measured 6.5 and 9.8 MB/s. The search page shows the host's own speed test (`inet_up`/`inet_down`), not
   the route to where your checkpoints go. **Feature:** show the API's advertised `inet_up`/`inet_down` beside a
   MEASURED upload (`vas --ssh --measure-up <url>`, a short timed upload from the box), so the gap is visible before
   a run is launched on it, not after.
5. **`-` in the log column is ambiguous:** no file matched the glob, or the file was empty. Say which.
   **Done 2026-10-16** (`probe::LogReading`), with the run's name in the cell (`s0/train.log: ...`), for
   askesis's Me36 rental of four sequential runs per box.
6. **A box can read 100 % GPU with 0 MiB used** (a transient sample while nothing held VRAM). One `nvidia-smi`
   sample is not a state; `--watch` should show the trend (hypomnesis's lesson: a single sample is not a diagnosis).
   **Done 2026-10-18**: `vas --ssh --watch` shows a `TREND` column, the last six samples of each box.

## Next feature (Éric, 2026-10-16): `vas check`, the box against your requirements

Our askesis preflight caught box 2's 1.5 MB/s uplink only AFTER renting, and only because that script
measures it. The search page shows advertised numbers. The generalisation:

```toml
# .vas.toml (or --spec FILE)
[require]
gpu = "RTX 5090"
cuda_min = "12.8"
disk_free_gb = 20
ram_gb = 16
upload_mbps = { min = 5, to = "https://huggingface.co" }   # MEASURED on the box, not advertised
```

- **`vas check`:** probe each running box once over ssh and print PASS/FAIL per requirement, beside the API's
  ADVERTISED value (`inet_up`/`inet_down`, `cuda_max_good`, `disk_space`...). Box 2 would have read
  `FAIL upload 1.5 < 5 MB/s (advertised ...)` before anything was launched.
- **It stays read-only toward the account.** Open question: the measured upload needs a destination that
  takes a throwaway payload without the user's write token (a public sink, or a timed transfer as a proxy).
- **A later step:** the same spec filters OFFERS before renting (searching offers is a read too), so the
  search page's numbers are checked against the user's needs, and then measured again on the rented box.

## Built for the next rental: `vas offers` (evening)

The Me36 rental (three RTX 5090s, tomorrow) needs boxes that pass askesis's renting filters, and the
search page is where the Polish box's numbers looked good. The "later step" above, offers filtered
by the user's own needs, came first, as flags and a config file of flags rather than the TOML spec.

Probed before writing a line (unauthenticated `GET`s, 2026-10-16):

- **`GET /api/v0/bundles/?q=<JSON>` answers without a key.** The official CLI now `POST`s the same
  query; this `GET` form is its commented-out predecessor, still answered. So `vas offers` needs no
  key, sends none, and `vas` stays `GET`-only.
- **At most 64 rows per search, whatever `limit` asks, with `truncated: false`.** The server's
  `order` decides which 64; the identity search (every offer rentable now) fills all 64. A tool
  that trusted `truncated` would present a cut list as complete: `vas offers` says "64 returned,
  vast.ai's cap: the list may be cut (narrow the search)", and sends its `--sort` to the server.
- **`allocated_storage` prices that much storage into `dph_total`.** Unset, the CLI's 5 GiB; the
  footer names the storage priced in.
- The filters askesis rents by (`gpu_name`, `num_gpus`, `cuda_max_good`, `disk_space`,
  `reliability2`, `inet_up`, `geolocation notin`, `host_id notin`, `verified`) all work server-side;
  they are re-checked client-side anyway, so a filter the server silently stopped applying would
  show as rows "dropped here", not as wrong rows.

Live, keyless, after the build (20:34): the identity, 64 returned (the cap note); askesis's filters
without `--verified`, 23 offers; with it, 17, the cheapest at $0.775/h with 50 GB priced in. The
`VERIFICATION` column earns its place: without `--verified`, the four cheapest 5090s were all
`deverified`.

Still open from above: the ADVERTISED `inet_up` is what `--inet-up` filters on; the measured upload
(`vas check`) remains the next feature.
